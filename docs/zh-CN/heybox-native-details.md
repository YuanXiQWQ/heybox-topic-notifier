# 原生匿名详情服务

这个可选入口复用专用 Android 中官方小黑盒 App 的正常匿名 SDK 状态，在运行 Deno
服务的主机上请求公开帖子详情。它接入现有的鉴权详情接口，不读取账号数据库或通知配置。

它需要长期保留同一台 Android 的数据。当前实现不在服务器上独立生成 SDK
标识，也不负责创建虚拟机。部署前应确认所选 Android 环境能正常运行官方
App，并单独验证实际服务器出口；一次成功不能保证长期可用。

## 准备专用设备

1. 使用隔离、持久的 Android 实例，安装官方小黑盒
   `1.3.400 / build1149`，正常完成首次协议确认和匿名初始化，无须登录账号。
2. 为该实例准备可读取 App 自身缓存的 ADB
   连接，并固定设备序列号。不要连接个人日常使用的实例。读取程序不会提升 ADB
   权限、修改 APK 或安装拦截证书。
3. 把该实例 `config.xml` 中已有的 `device_id`
   保存到独立的设备绑定文件。绑定文件只能包含原来的 16
   位小写十六进制编号。该编号不是随机新建值；设备重建或 App
   数据丢失时应停止服务并重新评估，不能自动换身份。
4. 为详情接口单独准备一个仅服务账号可读的鉴权文件，内容为 32–128
   个字母、数字、下划线或连字符。它与 SDK 标识、用户登录凭据及 SSH
   密钥互相独立。

设备绑定与鉴权文件放在部署状态目录，不放进仓库、环境变量日志或聊天记录。Android
数据、绑定文件和鉴权文件应按各自用途保管；SDK 匿名标识由 App
自身保存，发布器只通过内存和子进程管道传递。

先执行只读检查。默认输出只有就绪状态和观察时间，不输出设备编号或 SDK 标识：

```sh
python3 -B scripts/read_heybox_native_session.py \
  --adb /path/to/adb \
  --serial YOUR_DEDICATED_DEVICE \
  --binding /private/state/native-device-id
```

## 启动详情服务

在设备和服务位于同一台主机时，发布器可以直接启动 Deno：

```sh
python3 -B scripts/pipe_heybox_native_sessions.py \
  --adb /path/to/adb \
  --serial YOUR_DEDICATED_DEVICE \
  --binding /private/state/native-device-id \
  --relay-token-file /private/state/native-detail-token \
  --start-app \
  -- deno task start:native-details
```

`--start-app` 只恢复已经绑定、已经接受协议的同一
App，不创建或清除设备数据。虚拟机本身及其 ADB
连接须预先启动；虚拟机重启后也应先恢复同一专用实例的必要读取权限。

当 Android 与请求出口分开时，`--` 后面可以改为已经配置好的 SSH
命令，在目标主机运行：

```sh
deno run --cached-only --no-config \
  --allow-net=api.xiaoheihe.cn,127.0.0.1 \
  /path/to/project/src/native_details.ts 8788
```

此时发布器运行在 Android 所在主机，Deno 通过 SSH
标准输入接收状态；帖子请求由运行 Deno 的目标主机发出。沿用已校验的 SSH
主机密钥和专用连接，不需要暴露 Android ADB、额外公网端口或任意代理接口。

入口固定监听 `127.0.0.1`。端口参数默认为 `8788`，可以使用其它非特权端口；`0`
仅适合需要随机端口的独立验证。服务只接受 `POST /v1/details` 的帖子编号，使用现有
Bearer 鉴权。启动前确认端口没有被其它实例占用。

正式接入时，主程序使用已有的配置：

```text
HEYBOX_GUEST_DETAIL_URL=http://127.0.0.1:8788/v1/details
HEYBOX_GUEST_DETAIL_TOKEN=<与独立鉴权文件相同的值>
```

通过部署系统的私密配置填写实际值，不把它们提交到仓库。主程序和独立详情服务的上线应分别验证；启动这个入口本身不会修改正式服务配置。

## 生命周期与限制

- 发布器默认每 60 秒重新观察同一 App 的缓存，`--refresh-seconds` 可设为 30–300
  秒。观察不会清除缓存或主动注册新身份。
- 读取器要求 App 的 `B` 前缀标识与 SDK 服务端缓存匹配，拒绝离线 `D`
  标识、版本不符和设备编号变化。缓存观察时间不等于标识签发时间或有效期。
- 详情服务只接受十分钟内的观察结果，并容许两台主机最多 30
  秒时钟偏差。缺少有效状态时返回未完成结果，不使用随机设备或摘要充当完整正文。
- 正常 SDK
  更新标识后，后续请求自动使用新快照；验证码或限流仍按既有规则冷却，更新快照不能提前结束冷却。不会因为验证码而重建设备。
- 发布器读取失败、SSH
  中断或输入结束时，独立服务关闭。启动器退出时等待服务结束；`--duration-seconds`
  可用于有时限的独立验证。
- 设备状态和已接受协议保留在原 Android 实例中。App
  或虚拟机重启后仍使用原绑定；应用和系统本身的兼容性、设备长期可用性以及 SDK
  标识的实际失效周期，需要在部署环境持续验证。

操作系统服务管理器可以负责运行既定启动命令，但不能把反复创建新设备或绕过上游验证当作恢复策略。

## 断线恢复与持久冷却

长期运行时，为独立详情服务指定一个专用冷却文件，并只授予该文件的读写权限：

```sh
deno run --cached-only --no-config \
  --allow-net=api.xiaoheihe.cn,127.0.0.1 \
  --allow-read=/private/state/native-retry.json \
  --allow-write=/private/state/native-retry.json \
  /path/to/project/src/native_details.ts 8788 /private/state/native-retry.json
```

文件由当前运行账号创建，保存设备绑定摘要、冷却期限及完整性校验，不包含 SDK
标识。请求上游前先同步落盘中断保护，响应完成后再保存实际冷却；进程在两者之间退出时，下一次启动会等待保护期限。文件采用独占锁，不能由两个详情服务共用；损坏、绑定不符或写入失败时停止取数，不自动清空检查点。

同一设备的后续启动必须复用同一个检查点路径。只运行一个详情服务，不通过另建文件或删除状态来结束冷却。状态目录须由运行账号独占管理；检查点损坏时保留现场并停止服务，不能以重连代替检查。

发布器增加 `--reconnect-attempts 5` 后，ADB 或传输暂时失效时先关闭现有服务，再以
30、60、120 秒等间隔重连，最多五次；每次退避上限十五分钟。可用
`--reconnect-delay-seconds` 调整初始间隔（15–300
秒）。自动重连会要求服务端配置上述冷却文件，不能退回无持久冷却的旧入口。

SSH 传输建议增加
`-o ServerAliveInterval=15 -o ServerAliveCountMax=3`，使失联连接能够及时退出。仍须保留主机密钥验证。设备编号、协议状态或
App 版本不符时直接停止；不会清理 App 数据或选择其它设备。`--duration-seconds`
限制整个运行时间，重连不会重新开始计时。

`--start-app` 会恢复意外退出的同一 App；官方 SDK
自行更新标识后，发布器继续传递新的正常缓存。缓存观察过期、SDK
标识更新和服务端拒绝旧标识是不同事件：没有服务端拒绝证据时，不能把自动观察或正常重启称作真实过期续期。

服务端明确返回 `lack_token` 时，详情服务先保存冷却，再通知发布器。启用
`--start-app` 的发布器等到冷却结束，正常重启同一 App，并等待 SDK
缓存出现不同的新值；如果 SDK 已自行更新，则直接使用该值。观察时间改变本身不算
SDK 刷新。没有启用
`--start-app`、刷新超时或新值再次被拒绝时停止，需检查实际设备和上游状态；不要让外部服务管理器反复重启这一停止状态。

验证码、限流与 `hkey` 不触发 SDK 重启。`lack_token`
也只说明服务端拒绝了该值，不能单凭这个状态断言原因是到期。发布器只接受固定结构的状态事件，输出不含
SDK 值，不能在传输命令的标准输出中混入其它文本。
